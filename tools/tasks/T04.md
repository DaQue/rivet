# T04 — fix the tag signature boundary, and make the tests enforce git's values

Owner brief. Read all of it before editing. Every "git said X" statement below was produced by
running real `git` (2.55) over these exact bytes and is reproducible; none of it is inferred.

## Why

`Tag::parse` scans for a signature marker with `armour.iter().find_map(...)` (tag.rs ~256-285).
That returns the **first** marker in *array order*, but real git keeps the **last** marker at the
start of a line, regardless of which of the four prefixes it is. So for a message that quotes one
armour block and then carries a real one, rivet splits in the wrong place: the message loses text
and `signature()` returns two blocks.

Verified against git (bodies in `crates/rivet-core/tests/fixtures/tag/`):

| body | marker order in body        | git's signature starts at | body bytes | git object id                        |
|------|-----------------------------|---------------------------|------------|--------------------------------------|
| N1   | PGP SIGNATURE, PGP MESSAGE  | the PGP **MESSAGE** line  | 242        | b68e4d033748a6fc04a44f69656a1ddc7ff6ed67 |
| N2   | PGP SIGNATURE, SSH SIGNATURE| the **SSH** line          | 240        | 0f8980b3e1b72f46d2f51c8d06d596d2235b79c8 |
| N3   | SSH SIGNATURE, PGP SIGNATURE| the **PGP** line          | 240        | 87e1dbebeb196b799ed2dcaee4d4f0ee8d0d3b1d |

N1 is the shape the current `parse_signed_tag` unit test uses. Git's answer there is that the
signature begins at the `-----BEGIN PGP MESSAGE-----` line, so that test's expectation is wrong
today — this task fixes both the code and that expectation.

Caveat for N1: git's reported signature for the nested body is the bytes from the PGP MESSAGE line
to the end of the body, i.e. 86 bytes including the final newline. `git for-each-ref
'%(contents:signature)'` strips the trailing newline, which is why the oracle prints 85.

## Change 1 — the scan

In `Tag::parse`, replace the first-match-by-array-order scan with a single left-to-right pass over
the message region that keeps the **last** offset at which any of the four markers sits at index 0
or immediately after `b'\n'`. Behaviour to preserve exactly:

- message   = `data[msg_start..abs_start]` (the newline before the marker stays in the message)
- signature = `data[abs_start..]` (runs to the end of the body)
- no marker anywhere -> message is the whole region, signature is `None`
- the returned `raw`, the field set, and the public API are unchanged

Do **not** edit doc comments (`///` and `//!`) anywhere — they are frozen pending owner approval.
You may correct a `//` implementation comment only where it states the wrong rule.

## Change 2 — unit tests in `tag.rs`

1. `parse_signed_tag` (~line 687) builds a nested PGP SIGNATURE / PGP MESSAGE armour. Under git's
   rule the PGP MESSAGE line is the marker, so:
   - `message()` == `b"the tag message\n-----BEGIN PGP SIGNATURE-----\n"`
   - `signature()` starts with `-----BEGIN PGP MESSAGE-----` and equals the rest of the body to
     the end, 86 bytes including the trailing newline
   Keep `is_signed()`, the byte round-trip and the id assertions as they are.
2. Add a test `parse_keeps_the_last_line_start_marker` covering both orders from the same headers:
   PGP block then SSH block -> signature starts with the SSH line; SSH block then PGP block ->
   signature starts with the PGP line. In both, the message is everything before the last marker.
3. Leave `parse_ssh_and_other_markers` and `parse_blank_line_in_message_does_not_end_it` alone —
   their single-marker cases are still correct.

## Change 3 — make the differential test actually differential

Gap: nothing in the suite compares against the `git_object_id` values real git recorded. Add:

1. `include_bytes!` constants `BODY_N1`, `BODY_N2`, `BODY_N3` (files already installed), each with
   its verified id in a trailing comment as above, and add them to
   `round_trip_is_byte_exact_for_every_body_git_accepts` and to `armour_detection_matches_real_git`
   (N1/N2/N3 are all signed).
2. A test `recorded_git_object_ids_are_reproduced` that:
   - reads `fixtures/tag/expected-object-ids.json` with `include_str!`
   - maps each key to its fixture body (`C`..`K`, `N1`..`N3`)
   - for every body `Tag::parse` accepts, asserts `tag.id(ObjectFormat::Sha1)? ==
     ObjectId::from_hex(ObjectFormat::Sha1, recorded)?`
   - for the four cases rivet rejects by contract (`D`, `F`, `J`, `K`) asserts the parse still
     errors, naming them in one explicit list so that changing either side fails loudly
   Parse the JSON with a small dependency-free line scanner (find `"<KEY>"`, then the next
   `"git_object_id": "..."` value). Do not decode `bytes_b64` — bodies come from the fixtures.

`documented_deviations_from_real_git` stays exactly as it is: whether rivet should also accept
D/F/J is a separate decision (T05) and is not in scope here.
