# T01c3 — fix octal mode parsing in `EntryMode::from_bytes` (REAL IMPLEMENTATION BUG)

## Situation

The two broken test call sites in `object/tree.rs` are fixed. But `cargo test -p rivet-core` is
still RED: **20 passed, 3 failed**. All 3 failures are in `object/tree.rs`'s test module, and all 3
fail inside `Tree::parse` with:

```
MalformedObject { kind: Tree, reason: "invalid mode at offset 0: tree entry  has invalid mode 304444" }
MalformedObject { kind: Tree, reason: "invalid mode at offset 0: tree entry  has invalid mode 116100" }
```

## Root cause (already diagnosed — do not re-investigate)

`crates/rivet-core/src/object/mod.rs`, inside `impl EntryMode`, function `from_bytes`, line 416:

```rust
let value = bytes.iter().fold(0u32, |acc, &b| acc * 10 + (b - b'0') as u32);
```

Git tree modes are **octal** ASCII (`100644`, `40000`, …), so the fold must accumulate in base 8.
In base 10, `b"100644"` becomes the decimal number 100644 — which is not any of the `0o…` constants
in the `match` below it, so the function returns `InvalidEntryMode`. The error formatter prints the
value in octal, which is why the failure text reads `304444` (= 0o304444 is 100644 decimal) and
`116100` (= 0o116100 is 40000 decimal). The doc comment above the function is already correct —
only the arithmetic disagrees with it.

## Required change

`crates/rivet-core/src/object/mod.rs`, line 416 only:

```rust
let value = bytes.iter().fold(0u32, |acc, &b| acc * 8 + (b - b'0') as u32);
```

Change nothing else in that function. Keep, exactly as they are:

- the `bytes.is_empty() || bytes.len() > 6` rejection with `mode: 0`;
- the ASCII-digit validation loop;
- the `match value` arms against `0o100755 / 0o100644 / 0o40000 / 0o120000 / 0o160000`;
- the `_ => Err(Error::InvalidEntryMode { name: BString::default(), mode: value })` arm.
- `name: BString::default()` — the caller in `tree.rs` wraps the error with its own offset, and the
  field name is part of the frozen `Error::InvalidEntryMode` shape. Do not add a `name` parameter
  to `from_bytes`.

Base 8 is also what makes the "optional leading zero" the doc comment promises work: `040000`
parses to 0o40000 = `EntryMode::Tree`, identical to `40000`.

## Also required — tests that would have caught this

`EntryMode::from_bytes` currently has **no unit test**, which is why the bug survived its own task.
Add `#[cfg(test)]` tests in `object/mod.rs` (append a `mod tests` if that file has none) covering:

1. each canonical spelling parses to the right variant: `b"100644"` → `Blob`, `b"100755"` →
   `BlobExecutable`, `b"120000"` → `Link`, `b"40000"` → `Tree`, `b"160000"` → `Commit`;
2. the leading-zero variant `b"040000"` → `Tree` (the doc comment promises this);
3. `b"100664"` is **rejected** with `Error::InvalidEntryMode` (the doc comment promises this too);
4. round-trip: for all five variants, `EntryMode::from_bytes(m.to_string().as_bytes()) == Ok(m)`.

Use the crate's existing `Result`/`Error` types and the existing import style in that file; add no
imports that are not already used there (`BString` is already imported).
